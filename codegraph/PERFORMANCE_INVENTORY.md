# CodeGraph application-wide performance inventory

Reviewed: 2026-09-28. Scope: production CodeGraph entry points, indexing, incremental updates, storage, mapped and daemon queries, CLI, visualizer, native mmap, and measurement tooling. This is an inventory and measurement ledger, **not** an approved fix plan. No format/version change or implementation is authorized by this file.

Status meanings: **confirmed** = current code performs the stated work; **candidate** = cost or replacement has not been established; **measured** = a named production-path receipt exists. A blank saving is not zero. Record before/after results on the same repository, operation, process temperature, and input before claiming an optimization.

## Scale target

End-to-end initial indexing must average **at most 0.1 ms of elapsed wall time per source file**, including startup, discovery, parsing, validation, and publication. That is at least 10,000 files/second: **87.7 ms for 877 files** and **13 minutes 20 seconds for 8 million files** if throughput stays constant. The earlier 8,254.70 ms / 877-file receipt is historical, **not the current baseline**. On the current checkout, an unprofiled MCP request exceeded the harness's 60-second timeout; the completed CPU-sampled MCP run took **107,205.21 ms / 877 = 122.24 ms/file**, about **1,222× above** the target. CPU sampling adds overhead, so that ratio is not an unprofiled speed claim. This is an acceptance target, not a claim that present architecture scales linearly or that each individual file finishes within 0.1 ms; parallel workers make per-file CPU time a separate metric.

Historical receipt: one host-level V8-profiled MCP lifecycle, one sample, 877-file D&D repository snapshot at commit `5bb50d41b68342fa8f0a6ce1d90ca05c35c65fa3`, `/private/tmp/codegraph-quant-CUDH10/report.json`. The latter's cold time rose to 655,993.08 ms under heavy instrumentation and is for attribution, **not** throughput comparison. Cold unprofiled direct-engine memory sampler: 96,925.04 ms, peak RSS **680,148,992 bytes**, peak main-thread heap used **51,556,560 bytes**, mapped/external accounting **1,095,831,271 bytes**; the latter is not resident memory. That sampler does not include the MCP transport. A separate 906-file live-tree sample is not mixed into this baseline. Work and allocation columns describe the **current path**, not guaranteed optimization savings. An observed operation time is only an upper bound on a subpath's possible saving. No costs are additive. For one-file edits, the memory goal is zero repository-sized temporary containers.

CPU-only V8 profile across the **whole** MCP lifecycle sampled main-thread GC **3.96 s** and semantic-worker GC **6.36 s**; main-thread `string` **5.89 s**, `intern` **5.01 s**, and `publicationEdges` **3.73 s**. These are sampled self-times, not elapsed phase times or additive savings, and this profile does not split cold from warm GC.
The heavily instrumented process trace contains **39,864.2 ms** of `V8.GCScavenger` event durations across the lifecycle. This is neither cold-only nor a wall-time saving estimate.

The ledger is grouped by entry point, **not ranked by presumed savings**. A whole-operation timer is never attributed to a listed subpath. “Repeated” includes multiple full passes (`mN`) as well as superlinear work; code complexity and estimated allocation counts flag investigation, not elapsed time. The 27 µs full-file load cited in discussion would be 23.679 ms for 877 files, but it is a different operation from semantic indexing or watcher publication and is not in these receipts. The 27,414.13 ms unlink result has no matching CPU/heap/trace artifact, so its cause remains unknown.

## Measurement queue, not fix order

1. Use the **one production MCP path** to record initial index and then warm single-file change, add, and unlink as distinct stages; capture CPU, heap, and trace for the **exact 27.4 s unlink case**. Split discovery, provisional, worker, acceptance, storage, cache publication, and first exact query (P01-P09, P22-P23); record per-file phase distributions to distinguish one slow file from repeated full passes. Assert exact changed/read/parsed/validated work sets.
2. Run a **separate restart/recovery experiment** only for startup and compatibility behavior (P01-P02, P05, P20-P21); do not mix its numbers into the one-file lifecycle baseline.
3. Capture **repeated query** costs for each MCP family and internals; record page CRC bytes, graph decodes, fallback opens, output size, and transport (P10-P13, P19).
4. Capture **CLI** correctness before timing it (P15), then **each visualizer route** first/repeat behavior and module scaling (P16-P17).
5. For each selected change, attach the same named baseline and after profile here: CPU, heap/allocation, GC, bytes/records visited, result parity, and version compatibility. Do not total overlapping profile frames. No file-format version change without explicit user approval and lossless migration.

The separate `docs/plans/` documents contain earlier proposed changes, including a version-4 proposal. They are **not evidence that those changes exist or authorization to make them**. Verify current code and obtain approval before any fix, especially a format change.
